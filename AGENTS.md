## DotNet

### Build and project files

- Build and test with `dotnet build` / `dotnet test` (SDK pinned in `global.json`). Never `msbuild` directly.
- All projects are SDK-style: files are included automatically, so never add `<Compile>` items.
- Shared settings (`net10.0`, `Nullable`, `LangVersion`, `TreatWarningsAsErrors`, version) live in `Directory.Build.props`. Don't repeat them in a `.csproj`.
- Warnings are errors. Fix the cause; don't suppress or add to `WarningsNotAsErrors`.
- Add packages with `dotnet add package` at an explicit version, and only with a reason.
- Use current C#: file-scoped namespaces, records, primary constructors, collection expressions, pattern matching, switch expressions, `using`/`await using` declarations.
- Nullable reference types are on. Model absence with `?`; don't silence warnings with `!` without a reason.
- `IOptions<T>` bound from `appsettings.json` / `appsettings.{Environment}.json`. No `ConfigurationManager`, `app.config` or config transforms.
- Secrets via user-secrets or environment variables, never in committed `appsettings`.

### Async

- Async all the way. Never block on a task with `.Result`, `.Wait()` or `.GetAwaiter().GetResult()`.
- Use `ConfigureAwait(false)` in `src/CodeTwin.Core`, `src/CodeTwin.Mcp` and `src/CodeTwin.Chat`. Never in `src/CodeTwin.Vsix` code that must resume on the shell's UI thread.
- Pass `CancellationToken` through every async call chain.

### Time, strings, culture

- Timestamps are UTC: `DateTimeOffset.UtcNow` or `DateTime` with `DateTimeKind.Utc`. Never local time.
- Always pass a `StringComparison` (`Ordinal` / `OrdinalIgnoreCase`; paths are case-insensitive on Windows).
- Pass `CultureInfo.InvariantCulture` explicitly for machine-readable text, even though `InvariantGlobalization` is on.
- Use `StringBuilder` for concatenation in loops; interpolation otherwise.

### Resources and I/O

- Dispose every `IDisposable`/`IAsyncDisposable` via `using`/`await using`. Implement `IAsyncDisposable` where cleanup is I/O.
- Stream files instead of buffering them into memory (archives, dumps, templates can be large).
- Expect Windows file-system behavior: files held open by others (`FileShare`), transient `ERROR_ACCESS_DENIED` on rename from antivirus scanners.

### Exceptions

- Catch specific exception types. Catching `Exception` is only for isolation boundaries (command executor, dump collectors, background loops), and must log.
- Never swallow an exception. Don't treat `OperationCanceledException` from a requested cancellation as a failure.

## Code style

- Apply OOP and Clean Code principles: small focused units, clear names, single responsibility.
- **Keep it simple. No overengineering.** Implement only what the task requires. Don't add abstractions, layers or configuration "for later".
- Keep inline comments to the strict minimum. Good names should make the code self-explanatory. Comment only non-obvious intent.

## Git

- Branches: `feature/<PascalCaseDescription>` from `main` (e.g. `feature/AddJobStore`). `hotfix/` and `release/` work the same way.
- Commit messages: <Imperative verb> <short description>`, single line, English, no trailing period (e.g. `Add OpenTelemetry wiring and a SQLite job store`).
- One focused change per commit. Formatting-only changes (`dotnet format`) go in a separate commit.
- **Leave no AI traces**: no `Co-authored-by` trailers, no "Generated by AI/Copilot" mentions, in commits, PRs or code.

## Communication

- Be concise. No filler, no restating the request, no long summaries.
- No emojis in responses.
- When a response covers several distinct points (questions, issues, proposals), number each one as `#1`, `#2`, ... so the user can reply and discuss them individually by reference. Keep the same numbers across the conversation.
- Don't just agree with the user. If you have a strong, well-founded opinion that differs, say so and argue it briefly with concrete reasons before proceeding.
- When unsure about an API, library or TwinCAT/Beckhoff behavior, look up the official documentation online instead of guessing.
